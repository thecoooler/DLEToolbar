# Участие в разработке

Спасибо, что помогаете DLEToolbar. Здесь описано, как сообщить о проблеме
и как прислать изменения.

## Сообщить о проблеме или предложить идею

- Перед созданием issue поищите похожие среди открытых и закрытых.
- Выберите форму: «Ошибка», «Предложение» или «Вопрос». Заполните обязательные
  поля: без версий DLE, PHP и плагина ошибку обычно не воспроизвести.
- Одна проблема — одно issue.
- Писать можно по-русски или по-английски.
- **Уязвимости не публикуйте в issue.** Порядок сообщения — в [SECURITY.md](SECURITY.md).

## Прежде чем писать код

- Для исправления очевидной ошибки можно сразу присылать pull request.
- Новую возможность или заметное изменение поведения сначала обсудите в issue.
  Так вы не потратите время на PR, который не подходит проекту.
- Если берётесь за существующее issue, напишите в нём об этом.

## Подготовка изменений

1. Сделайте fork репозитория и создайте ветку от свежего `main`. Название ветки
   отражает суть: `fix/skin-cookie`, `feature/sql-export`, `docs/install`.
2. Одна ветка и один PR — одна задача. Несвязанные правки отправляйте отдельными PR.
3. Следуйте правилам кода из [AGENTS.md](AGENTS.md). Они обязательны и для людей:
   работа напрямую с API DLE, без `declare(strict_types=1)`, без лишних проверок
   окружения и подавления ошибок через `@`.
4. Не ослабляйте проверку прав доступа, CSRF-токена, нормализацию настроек
   и экранирование HTML.
5. Если меняется поведение, обновите [README.md](README.md) и при необходимости
   [CONTEXT.md](CONTEXT.md) в том же PR. Для изменений интерфейса приложите
   скриншоты.

## Проверка

Нужен [dleplugin](https://github.com/thecoooler/dleplugin) v0.3.1 или новее
и Docker для тестов.

```sh
dleplugin test                       # тесты Pest
dleplugin static                     # статический анализ для PHP 8.4
dleplugin static --php-version 7.4   # статический анализ для PHP 7.4
```

Новое поведение покрывайте тестами в `tests/`. Изменения SQL-панели проверяет
браузерный тест `tests/browser/`. CI запускает все проверки для каждого PR;
PR сливается только при зелёном CI.

Если можете, проверьте изменение на живом сайте DLE и укажите в PR версии DLE
и PHP, на которых проверяли.

## Коммиты и pull request

- Заголовок PR — на английском, в повелительном наклонении, до ~70 символов:
  `Fix template switching on DLE 13.0`. Он станет сообщением коммита в `main`.
- Описание PR — по-русски или по-английски, по шаблону: что изменено, зачем,
  как проверено. Если PR закрывает issue, укажите `Closes #N`.
- PR сливается через squash: вся ветка становится одним коммитом в `main`,
  поэтому промежуточные коммиты можно не причёсывать.
- Не переписывайте историю ветки после начала ревью без необходимости:
  ревьюеру проще смотреть новые коммиты поверх.
- Для первого PR от нового участника GitHub запускает CI после одобрения
  мейнтейнером — это нормально.

## Релизы

Релизы выпускает мейнтейнер тегом `vX.Y.Z` из `main`; порядок описан в README.
Номер версии в PR менять не нужно.
